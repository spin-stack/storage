# INVARIANTS

Invariants extracted from the architecture doc (§4/§5/§12/§14/§21/§27). Each is a
property a **checker** verifies inside the DST harness. An invariant is born
`pending` and becomes `active` when its checker runs in CI. The **standard gate**
(PLAN §2) requires all `active` checkers green.

**Checker states:** `pending` (no checker yet) · `active` (checker runs in CI) ·
`n/a-until` (subject does not exist yet; activated by the named phase).

## Notes on activation

- **Phase 01 activates the *framework*, not the data invariants.** It makes INV-01
  (lint) and INV-02 (deterministic replay) active, and ships the checker harness with
  at least one trivial checker wired end-to-end so later checkers are a fill-in, not a
  retrofit. This is the whole point of §25.1: "retrofitted checkers, no; the harness
  and checkers existing first, yes."
- Each later phase's `PHASE-0N.md` lists exactly which invariant IDs it flips from
  `pending`/`n/a-until` to `active`, and the standard gate then requires them.
- When an invariant's checker cannot yet be expressed (Harness-agent veto), the
  increment returns to the Planner rather than shipping the invariant as prose only.
