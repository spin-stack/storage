# TEST-GAPS — failure modes the suite does not cover

Produced 2026-07-25 by a six-way audit of the test suite (one agent per subsystem),
each finding then checked by an adversary whose default was that the claim is wrong.
78 gaps survived that check. This file is the backlog; it is not a wish list of "more
tests" — every entry is a concrete sequence of events with a bad outcome.

The audit's premise, and the one to keep: **assume the worst operational case**. The
happy path is already covered by 280+ tests. What was missing is what happens when a
disk tears a write, a response is lost twice, an operator runs two things at once, a
backend throttles mid-sweep, or a clock moves backwards.

## Already fixed (in the order they were closed)

| Finding | Commit |
|---|---|
| A rejected append left its bytes in the log: replay resurrected a record the guest was told failed (duplicate sequence, different content) or stopped at the tear and silently dropped everything after it | `5890963` |
| The uploader compared an ETag against a SHA-256, so one lost PUT response would report a byte-perfect object as divergent and wedge the volume forever on real S3 | `8428b4a` |
| The GC did not treat the durable prefix as a root: a sweep delete-markered every ACKed WAL object no checkpoint enumerates, moving the durable point to zero | `8dd3de3` |
| A drain could record an immutable epoch boundary of 0 below what the volume had durable, losing it permanently | `8dd3de3` |
| Nine of eleven DST checkers had never been shown to catch anything | `b54e66e` |

## Open

Grouped by severity, then subsystem. Each entry names the failure mode, what breaks,
and where the test belongs.


### CRITICAL

- **checkpoint.Create trusts the log's local durable watermark instead of the S3 prefix, then unlocks local truncation over data S3 does not have** _(recovery-materialize)_
  - failure mode: S3's contiguous prefix falls behind the log's durable watermark (a GC mark on the un-checkpointed tail, a mis-scoped lifecycle rule, a corrupt object, an ACKed PUT whose object was later lost). The next checkpoint publishes the higher sequence with a gapped object list — the RootDigest matches because it is a hash of key strings and cannot express a hole — then advances published, which authorises TruncateLocal over sequences whose only remaining copy was local. INV-13's "never truncate above a verified published point" is enforced against a number nobody verified. The published checkpoint is also create-only and immutable, so it is permanently unusable for rebuild.
  - missing test: In internal/checkpoint/checkpoint_test.go: flush 3 objects, delete-mark (or corrupt) the middle one, call Create, and assert (a) it refuses or clamps DurableSequence to recovery.DurablePoint, (b) published is not advanced past the S3 prefix, (c) TruncateLocal at the log's durable is still refused with ErrTruncateAboveDurable. Plus an assertion that any published checkpoint's Objects list is contiguous from the epoch floor to DurableSequence.

- **Recovery and materialization never chain across epochs: a volume that has ever been promoted rebuilds with only its newest epoch's writes** _(recovery-materialize)_
  - failure mode: Every failover, drain, or host evacuation after the first one materializes a volume containing only the writes made since the last promotion, and reports it as a complete rebuild (Progress.UpTo equals that epoch's durable point). Nothing errors, so an operator has no signal. A volume moved twice loses everything written before the second move.
  - missing test: A recovery test and a materialize test at epoch >= 2 that write bytes in epoch 1, cross the boundary via a recovery point, write more in epoch 2, and assert the pre-promotion bytes are present in the recovered/materialized view — or an explicit, tested refusal to materialize an epoch whose predecessor is not covered by a checkpoint/snapshot the caller also fetched. Plus a drain test that moves the same volume twice and asserts the second move's Bytes/UpTo cover the first epoch's ACKed data.


### HIGH

- **Capacity released twice when the progress record fails after a completed move** _(drain-placement-dst)_
  - failure mode: Without slack the second release hits ErrCapacityUnderflow, which every later pass returns forever: the operation never reaches SUCCEEDED, the host stays DRAINING, and the remaining volumes are never evacuated. With slack it silently eats another volume's reservation and placement over-fills the host. This is the exactly-once claim DEV-0008 was closed on.
  - missing test: internal/controlplane/drain_test.go: reconstruct 'promoted + boundary written + capacity released, progress NOT recorded', resume the same operation id, and assert the source's committed bytes moved by exactly one volume size; plus a test where Cancel lands between move() returning and the progress write.

- **finishMovedVolume writes an epoch boundary for a volume some other actor moved** _(drain-placement-dst)_
  - failure mode: The boundary object is authored by a party that fenced nobody, and it is create-only. Because prefixFloor (recovery.go:148-156) makes RecoveredUpTo+1 the floor of the epoch's own prefix, a boundary that understates the previous epoch collapses the live epoch's contiguous prefix to zero — DurablePrefix returns 0 and every ACKed write in that epoch is invisible at recovery. If instead the legitimate promoter writes its (correct) boundary later, it fails forever with the 'different recovery point' hard error at drain.go:345-348 and the failover wedges. Either way, silent under-reporting of durability on a volume this drain never fenced.
  - missing test: A drain whose plan contains V where a concurrent failover promotes V elsewhere: assert the drain refuses to write V's boundary and refuses to release capacity for it — i.e. finishMovedVolume must prove *this operation* performed the promotion (a per-volume marker in progress), not infer it from current ownership.

- **An operation id reused for a different host drains the wrong plan and bills the wrong host** _(drain-placement-dst)_
  - failure mode: An operator retry with a copy-pasted id, a replayed request, or a UI keyed on the wrong entity makes host B pay for host A's volumes: B's reservations are decremented for volumes it never held (later releases then underflow and wedge), create-only boundary keys are burned on the volumes' live epochs, and the call reports SUCCEEDED with fabricated Move records.
  - missing test: Drain(term, hostB, opIdRecordedForHostA) must fail with a host/plan mismatch error; assert host B's committed bytes are untouched and no recovery-point object was written.

- **The drain only ever fences a dead source: no lease revocation, and a renewal can land under the promotion** _(drain-placement-dst)_
  - failure mode: (a) A healthy host cannot be evacuated at all — the operation spins forever and the runbook's 'drain before maintenance' has no mechanism to stop the renewals. (b) A renewal that lands between the drain's read and Promote leaves the source's monotonic lease valid past the promotion: the source keeps ACKing FLUSHes into the old epoch while the destination writes the new one, and everything ACKed above the recorded RecoveredUpTo is discarded at recovery. Compounded by the lease being per host: fencing one volume needs every other volume on that host fenced too.
  - missing test: (1) a drain where the source renews its lease during the pass, asserting the drain either revokes it term-guarded or refuses to promote; (2) a DST scenario giving the source a real lease.Manager and having it attempt Write+Flush after the drain, asserting wal.ErrSelfFenced and emitting EventDurableAck{LeaseValid}/EventFailover so the INV-06/INV-09 checkers can see it.

- **Two concurrent promotions double-bump the epoch: BumpVolumeEpoch has no expected-epoch predicate** _(drain-placement-dst)_
  - failure mode: A drain and a failover (or two drains) reconciling the same volume inside one CP term leave PG and the S3 epoch object diverged by one and PG naming a primary that was never granted anything. The divergence is then indistinguishable from a legitimate resume, so the next promotion grants the epoch to a third host while the previous winner still holds a valid host lease and keeps ACKing — two writers, and a recovery point chained from the wrong epoch.
  - missing test: Two Promoters (or a drain plus a failover) interleaved on one volume, asserting exactly one epoch is granted; and a query-level compare-and-set (... AND current_epoch = $expected) with a test that a bump from a stale expected epoch affects 0 rows.

- **UpsertHost overwrites nvme_committed_bytes and wedges an in-flight drain** _(drain-placement-dst)_
  - failure mode: Any concurrent host update (re-registration, a state refresh, an Agent heartbeat once it exists) resets committed bytes mid-operation. Downwards it makes the drain's release underflow — ErrCapacityUnderflow on every subsequent pass, host stuck DRAINING with volumes still on it; upwards/away it erases the destination's reservations so placement over-fills the host past the declared oversubscription ratio.
  - missing test: A metadata-level test that UpsertHost cannot change nvme_committed_bytes (the heartbeat path must not write that column; only CommitHostCapacity may), and a drain test with an UpsertHost between passes asserting the committed bytes are preserved and the drain completes.

- **Two drains on the same host are neither refused nor serialized** _(drain-placement-dst)_
  - failure mode: An operator (or a reconciler that lost track of its operation id) starts a second drain: the source's capacity is released twice per volume — underflow and a permanently failed operation, or the silent consumption of other volumes' reservations — and the losing destination's reservation is never released, because the loser's release() path is skipped once the volume is off the source. Concurrently, both drains call Promote on the same volume, which is the double-bump above.
  - missing test: A second Drain of a host with a live drain operation must be refused (or serialized); assert capacity is still released exactly once and no second destination is reserved.

- **DST: no drain crash-boundary scenario exists, though REBASELINE step 2 requires one** _(drain-placement-dst)_
  - failure mode: Every exactly-once claim the drain rests on (capacity released once, one epoch granted, one boundary object with the right PrevEpoch/RecoveredUpTo) is unproven at every boundary except one — and the very next boundary is broken today (the double release above), which is what an uncovered boundary costs. A regression at any of the remaining five ships green.
  - missing test: A DST scenario that, for each boundary in move() (after reserve, after bulk materialize, after promote, after the final materialize, after the boundary write, after the release, after the progress record), aborts the pass, resumes the same operation id, and asserts: the source's committed bytes moved by exactly one volume size, exactly one epoch was granted, exactly one recovery-point object exists with the expected PrevEpoch/RecoveredUpTo, and the operation reaches SUCCEEDED.

- **lease.Manager.Renew() has no expiry guard and anchors t0 to the response instant, so a late renewal outlives the CP's fencing deadline** _(fencing-promotion)_
  - failure mode: Heartbeat renewal reaches the CP at T+8 (last_renewal=T+8); the response is delayed 5 s (GC pause / PG failover retry / partition heal) and the agent calls Renew() at T+13, extending its monotonic validity to T+23. The CP's fencing deadline is T+20, so a promoted writer starts at T+20 while the old agent still ACKs FLUSH until T+23 — its post-boundary objects extend epoch N's prefix past the recovery point the new writer materialized. ACKed writes lost (INV-06/INV-09).
  - missing test: internal/lease/lease_test.go: a TestValidity case `{"renew after expiry does not resurrect": Grant(); clk.Advance(11s); Renew(); want valid=false}`; a property/unit test that agent validity never exceeds cp_last_renewal + ttl once Grant/Renew take the request instant (or a CP-supplied deadline) instead of no argument; and a DST scenario `late-lease-renewal` where the renewal response lands past the fencing deadline and DurableAckLeaseChecker/NoLostAckedWriteChecker must fire.

- **Nothing can revoke or refuse a host lease: RenewHostLease has no host-state predicate, so a re-granted lease un-fences a source whose volume was already promoted away** _(fencing-promotion)_
  - failure mode: HostA loses CP connectivity long enough for its lease to go stale; the drain promotes volume V to hostB and records the epoch boundary. Connectivity returns, the ordinary heartbeat renews hostA's lease (no state guard, hostA is legitimately serving its other volumes), lease.Manager.Valid() is true again, and hostA's wal.Log for V — never self-fenced because no Flush hit the dead window — resumes ACKing FLUSH into wal/V/N/ after hostB already materialized epoch N up to the boundary. Both hosts ACK; hostA's ACKed writes are outside what hostB recovered.
  - missing test: A metadata.Store test (both sim and pg) that RenewHostLease is refused for a host in CORDONED/DRAINING/DEAD, plus a revoke/expire path on the interface; and a drain test / DST scenario where the source's log writes+flushes after Drain returns and must fail (ErrSelfFenced or an epoch/lease-generation check) rather than ACK.

- **Promote() has no expected-from-epoch guard and trusts a caller-supplied renewedAt, so an overtaken promotion fences a healthy, just-promoted writer** _(fencing-promotion)_
  - failure mode: Two drain passes (or CP goroutines) both observe V on hostA. Pass 1 promotes V to hostB: epoch 4, lease granted to hostB, hostB starts recovering and ACKing. Pass 2 then calls Promote(V, renewedAt=hostA's stale last_renewal, hostC): stored==pg==4, primary hostB != hostC, so it bumps to 5, CASes S3, and grants hostC a lease — with zero fencing wait, because the timestamp it was handed belongs to hostA, not to hostB whose lease was granted seconds ago. hostB keeps ACKing epoch 4 for a full lease TTL while hostC writes epoch 5 and computes its recovery point from epoch 4's prefix. Lost ACKed writes, and the volume ping-pongs on every duplicate.
  - missing test: `TestPromoteRefusesWhenTheVolumeMovedOnSinceTheCommandWasIssued` — expect-from-epoch 2 after the volume already reached epoch 3 on another host must be a no-op error, not a new epoch; and a test that the fencing wait is measured against the lease of the host actually being fenced (read by the promoter) rather than a caller-supplied instant.

- **A missing host_leases row makes the fencing wait zero — fail-open exactly after a metadata restore** _(fencing-promotion)_
  - failure mode: After a PG PITR restore to a point before the lease insert, or an operator cleanup of host_leases, the source host is alive and its agent-side lease.Manager is still valid for up to lease_ttl on its monotonic clock. A drain or promotion issued right then gets renewedAt = zero, skips FENCING_WAIT entirely, and grants epoch N+1 immediately. Two writers for a full lease TTL, at the exact moment the CP's view of the fleet is least trustworthy; every FLUSH the old writer ACKs in that window is outside what the new writer recovered.
  - missing test: `TestDrainRefusesWhenTheSourceLeaseRecordIsMissing` (delete the lease row in newDrainWorld) — with no lease row promotion must wait a conservative lease_ttl + max_clock_skew from now, or refuse until the host is observed dead, instead of proceeding instantly; plus a DST scenario pairing a rebuilt/restored CP with a live source writer.

- **epoch.Current reads the body with Get and the ETag with a separate Head, so two promoters can grant the same epoch to two hosts; the epoch record names no owner** _(fencing-promotion)_
  - failure mode: Two promoters (two drain passes, two reconciler goroutines) race on one volume; one of them pairs a stale epoch body with a fresh ETag, wins the CAS, and grants a lease for an epoch another host already owns. Both writers PUT into wal/<vol>/4/ with independent sequence numbering; the contiguous-prefix computation mixes or truncates them and the durable point belongs to neither. Both pass every fence the system has, because no fence records who holds the epoch.
  - missing test: A concurrency test that two simultaneous promotions of one volume leave exactly one host able to publish (requires the epoch record to carry its holder and Verify to check it, and Current to be a single atomic read returning body+ETag).

- **wal.Uploader treats the object-store ETag as a SHA-256 checksum, so on real S3 every lost-response retry becomes a hard ErrDivergentObject** _(fencing-promotion)_
  - failure mode: Against a real S3/MinIO backend the §14.5 case the code exists to handle — PUT persisted, response lost, retry sees 412 — HEADs the object and compares an MD5 to a SHA-256. They never match, so Upload returns ErrDivergentObject: Flush does not advance durable and returns a hard corruption error, so the volume's FLUSH path fails permanently on the first lost response, and an operator debugging a data-loss-flavoured error is likely to force something worse.
  - missing test: Run wal.Uploader (including the lost-response 412 reconcile) in the integration lane against the certified backend, and verify object identity by a stored checksum in object metadata / the object's own header digest rather than by the ETag.

- **The production S3 store can permanently delete: no versioning check anywhere, no Restore, and the only test of S3Store.Delete runs on a non-versioned bucket** _(gc-objectstore)_
  - failure mode: A bucket created by tooling that forgets versioning, or whose versioning an operator Suspends, turns every GC reachability bug (starting with finding 1) from 'restore the version' into permanent destruction of ACKed data — while INV-14 is documented as structural ('the interface deliberately cannot reach permanent deletion'). And because S3Store has no Restore, the operator action the whole INV-14 argument rests on does not exist on the production path at all.
  - missing test: integration/backend: run storetest.RunContract against S3Store on a *versioned* bucket, extended with delete → ListObjectVersions → restore-by-VersionId; a case on a versioning-Suspended bucket asserting the store refuses to operate. A unit test that NewS3Store fails when GetBucketVersioning is not Enabled. A structural test that every objectstore.Store implementation also implements Restore (today it would fail on S3Store).

- **An unparseable or digest-mismatched manifest/checkpoint silently orphans everything it anchors** _(gc-objectstore)_
  - failure mode: A half-written manifest (the filesystem store writes with a bare os.WriteFile — see finding 11 — or an interrupted multipart upload, or a future schema/encryption change) anchors nothing. Every WAL object it protected becomes a mark candidate and the snapshot's live data is deleted because its index was unreadable. The correct behaviour for an unreadable anchor is to abort the sweep, never to widen it.
  - missing test: internal/gc: table-driven cases for an anchor body that is truncated, empty, non-JSON, valid JSON missing `objects`, and valid JSON whose RootDigest does not match — each must make Reachable/Mark return an error and mark nothing. Plus a manifest that disappears between List and Get.

- **The WAL uploader reconciles a lost-response retry against the sim's sha256 ETag, which real S3 never returns** _(gc-objectstore)_
  - failure mode: The §14.5 'PUT persisted, response lost' path — the single most common S3 failure — takes the 412 branch on retry, HEADs, sees a quoted MD5 where it expected a sha256, and returns ErrDivergentObject. Flush never ACKs and the volume stalls; or someone deletes the check to make it pass and duplicate/divergent objects stop being detected. Either way the durability path behaves differently on a real backend from every proof written about it.
  - missing test: storetest must pin ETag semantics (Head-after-Put equality plus an explicit 'opaque, not a content hash' statement), and the integration lane must run wal.Uploader against S3Store: upload, re-upload the same batch (idempotent success), upload different bytes at the same key (ErrDivergentObject), including an object above the multipart threshold.

- **The grace period is never exercised against clock skew or a publication that outlasts it** _(gc-objectstore)_
  - failure mode: (a) The GC host's clock runs ahead of the backend's: `now.Sub(info.LastModified) >= grace` for objects written seconds ago, the window collapses to zero and the objects of an in-flight publication are marked. (b) A publication legitimately outlasts grace (throttling, retried multipart, a large snapshot) — §21.1 writes objects first, so by the time the manifest lands the objects are already older than grace. Both are the finding-1 outcome with no reachability bug at all. (c) Clock jumps backwards: the difference is negative, everything is protected forever and the bucket grows unbounded with no signal.
  - missing test: internal/gc: a store whose timestamps come from a different clock than Mark's (skew ±grace both directions), a clock that moves backwards between sweeps, and a 'publication in flight longer than grace' case (objects present and aged, manifest published only afterwards) asserting nothing anchored is marked. A DST scenario running the GC concurrently with a snapshot publication, with a non-zero grace and a store clock actually installed.

- **The filesystem store's create-only PUT and If-Match CAS are check-then-act and admit multiple winners** _(gc-objectstore)_
  - failure mode: Create-only is what makes a retried WAL upload and a published manifest immutable (INV-21, INV-16); the ETag CAS is the §12.4 epoch fence (INV-10). On this store two promoters can both win epoch.CompareAndAdvance — split brain, two writers believing they hold the fence — and a published manifest or checkpoint can be silently overwritten by a concurrent writer. Both are silent: every caller gets err==nil.
  - missing test: storetest (so every implementation runs it, including S3Store in the integration lane): an N-goroutine create-only race asserting exactly one winner and that the stored body is the winner's, and an N-goroutine If-Match race on one ETag asserting exactly one winner. Run under -race with -count>1.

- **No shared contract test for metadata.Store; sim and pg demonstrably disagree** _(metadata-cp)_
  - failure mode: A DST scenario or unit test proves a fencing/idempotency property against the sim; the same call sequence in production either hard-errors (23505/23503), or returns a different error identity, or — for term 0 and RecordOperation-under-stale-term — takes the opposite branch. The proof does not transfer.
  - missing test: internal/metadata/metadatatest with RunContract(t, func(*testing.T) metadata.Store), invoked from a sim unit test and from an integration-tagged pg test, pinning at minimum: duplicate CreateVolume/CreateSnapshot, ErrStaleTerm on every mutation including RecordOperation/CreateSnapshot/UpdateOperation, missing-row error identity, FK/ghost-id behaviour, term 0 before any election, empty and malformed ids.

- **Drain double-releases source capacity across the crash boundary between the release and the progress record** _(metadata-cp)_
  - failure mode: Source host holds 3 volumes' worth of committed bytes; drain releases volume v1's bytes, the CP dies before writing progress. Resumed pass releases v1 again: the source's nvme_committed_bytes is now short by one volume, so placement overcommits it — or, if the books are tight, the non-negative guard turns the release into ErrCapacityUnderflow and wedges the drain permanently (the behaviour TestDrainSurfacesBrokenCapacityAccounting shows is a hard error).
  - missing test: A drain test that fails/aborts the pass after move() returns but before d.record() writes progress.Moved, then resumes and asserts the source's committed bytes dropped by exactly one volume; plus a store-level test that a stale current_state cannot overwrite a newer one (needs a version column or a CAS predicate on the UPDATE).

- **rebuild-metadata never corrects an existing volume row whose epoch is behind S3, and reports success** _(metadata-cp)_
  - failure mode: PITR restore rewinds volumes.current_epoch from 5 to 2 while S3's epoch object still says 5. The operator runs rebuild-metadata, which returns success with Volumes:0 and an empty NotReconstructible for that volume. Every subsequent Promote returns ErrEpochConflict, and there is no code path anywhere that can set the epoch to 5, so the volume is permanently unattachable — during the exact incident rebuild-metadata exists for.
  - missing test: A rebuild test with a pre-existing volume row whose current_epoch is behind the S3 epoch object, asserting the row is corrected or the volume id appears in NotReconstructible; and a rebuild interrupted partway (leadership change or one unreadable manifest) followed by a re-run, since there is no transaction around the create loop.

- **materialize replays WAL objects with no integrity validation — the DEV-0003 fix was never mirrored out of internal/recovery** _(recovery-materialize)_
  - failure mode: A snapshot manifest or checkpoint is published while its objects are valid. Later one of those objects is rewritten/torn/restored-to-a-wrong-version in the bucket. The manifest digest is computed over key strings only (snapshot.Digest / checkpoint.Digest), so it still matches. A cross-host clone or standby hydration calls FromSnapshot/FromCheckpoint: the header still claims the full span, wal.Replay stops cleanly at the torn record, and materialize returns err=nil with Progress.UpTo equal to the header's LastSequence. The destination boots a volume missing ACKed writes while reporting it covered the full sequence. In the cross-volume variant, a body belonging to another volume/epoch stored at this volume's key is replayed into the view — and a plaintext volume has no DEK to fail closed on.
  - missing test: In internal/materialize/materialize_test.go, next to TestFromSnapshotRefusesSequenceGap: (a) a manifest/checkpoint referencing an object with a valid header and a truncated payload → must fail, not return a short view; (b) the same with a single flipped payload byte (digest mismatch); (c) a header whose LastSequence/RecordCount exceed the records it carries; (d) a referenced object whose header VolumeID or Epoch belongs to another volume/epoch. All four are already covered on the recovery side by internal/recovery/integrity_test.go — the fix is to export recovery.validate (or a Verify helper) and call it from fetchAndReplay, with the tests mirrored.

- **materialize has no prefix floor: a manifest or checkpoint whose objects start above sequence 1 rebuilds a volume with a hole at the front** _(recovery-materialize)_
  - failure mode: A manifest or checkpoint that lost its early objects (aborted GC, partial bucket restore, mis-scoped lifecycle rule, or a checkpoint built by the over-claiming Create) materializes as a valid volume on the cross-host clone and drain paths. The caller is told the state covers up to the last sequence while everything before the first surviving object simply does not exist in the rebuilt volume.
  - missing test: Mirror internal/recovery/integrity_test.go TestPrefixRequiresItsFloor in internal/materialize: a manifest/checkpoint whose object run starts above the epoch floor (sequence 1, or recovery_point(epoch).RecoveredUpTo+1) must be refused; and assert Progress.UpTo equals the manifest's TargetSequence / the checkpoint's DurableSequence, which is the cheap cross-check that catches both this and the gapped-checkpoint case.

- **prefixFloor swallows every error from ReadRecoveryPoint and silently falls back to floor 1** _(recovery-materialize)_
  - failure mode: A transient backend failure (§24 throttling is explicitly modelled) or a cosmetically damaged recovery-point object collapses the epoch's floor from recovered_up_to+1 to 1. The epoch's objects legitimately start above that, so they no longer reach the floor and the contiguous run returns nothing: DurablePrefix reports 0 with a nil error, giving the caller nothing to retry on. Fed into drain, that becomes an immutable recovery point of 0 for the next epoch and buries every ACKed write below the new floor permanently.
  - missing test: Two cases in internal/recovery/integrity_test.go: (a) InjectThrottle on the recovery-point GET and (b) a corrupt/truncated recovery-point body — each asserting DurablePrefix/DurablePoint return an error rather than a silently lower floor, i.e. that a store error is never conflated with objectstore.ErrNotFound.

- **The recovery-point chain is never checked for monotonicity or linkage across three or more epochs** _(recovery-materialize)_
  - failure mode: One bad pass — from the empty-epoch bug, the swallowed floor error, a stale LIST, or a GC-shortened prefix — writes an immutable boundary lower than an earlier one, or one whose PrevEpoch does not chain. The floor for the newest epoch then either sits below data that was already superseded or (a floor of 0/1 against objects that start higher) declares nothing durable at all, permanently, with no in-band repair because the object is create-only. This is the one guard that would have caught gaps 3, 5, 9 and 12 at the boundary write instead of after it.
  - missing test: A chained recovery test over epochs 1→2→3 asserting recovered_up_to is non-decreasing and PrevEpoch links (N+1's prev == N), plus a drain test that refuses to write a boundary below recovery_point(prevEpoch).RecoveredUpTo — and a DST invariant checker for boundary monotonicity with a planted-bug proof.

- **KeyID semantics on the write path are unvalidated: a KeyID-0 DEK ACKs a FLUSH whose object recovery can never read** _(wal-durability)_
  - failure mode: A volume configured with a DEK whose KeyID is 0 (or an Encryption enabled after NewBatcher was given a different keyID) ACKs FLUSH as remotely durable while every uploaded object fails recovery.validate — an ACKed write that S3 provably cannot produce, with no error at write time, no error at ACK time, and a durable point stuck at 0. Separately, Decrypt attempts Open for any non-zero KeyID it does not hold, so a mixed-KeyID epoch aborts the entire Recover instead of reporting which key is missing.
  - missing test: In internal/wal/crypto_wal_test.go: (a) a round-trip that writes through an encrypted Log, uploads, and asserts recovery.DurablePrefix/Recover return the written data — run for KeyID 0 and non-zero; (b) assert EnableEncryption with DEK.KeyID==0 (or a batcher keyID that disagrees with the DEK) is refused at configuration time; (c) assert Decrypt rejects a record whose KeyID it does not hold instead of calling Open.

- **INV-04's backpressure accounting is cleared by events that make nothing durable, and wal_durable_gap_bytes reports 0 (or nothing) exactly where the doc calls it critical** _(wal-durability)_
  - failure mode: On a `local` volume (or a `remote` volume during an S3 outage where anything calls Sync), the un-remote-durable backlog grows without bound while the RPO gauge reads 0 or is never published, so §5.7's 'explicit error rather than silently filling NVMe' never fires and the operator's only RPO signal is a lie. Host loss then loses far more than max_unflushed_age of ACKed FLUSHes. (The absence of the async uploader itself is DEV-0007; the metric definition and the unbacked accounting reset are not.)
  - missing test: A test asserting wal_durable_gap_bytes equals the bytes not yet in a verified S3 object (not the unsynced bytes) after N local-mode flushes with the store unreachable, that the gauges are recorded in local mode at all, and that Sync() does not clear the remote-durability accounting; plus a bound on Batcher.pending bytes with an explicit error.

- **A fenced writer's late PUT raises the old epoch's durable prefix past the recovery point** _(wal-durability)_
  - failure mode: W1's in-flight PUT (slow S3, SDK retry) completes after W2 wrote recovery-point{recovered_up_to: D}. materialize.FromEpoch(vol, oldEpoch) — the drain/warm-standby source per ADR-0008 — calls DurablePoint, which does not consult the next epoch's boundary, so it rebuilds a state containing a record the live epoch-N+1 volume never had. Two divergent materializations of the same volume from the same bucket; and a drain resumed through finishMovedVolume recomputes prog.UpTo, finds it disagrees with the existing create-only recovery point, and hard-errors that volume permanently.
  - missing test: A DST scenario that lands W1's fenced PUT *after* W2's recovery point and asserts either that DurablePrefix(epoch N) is clamped to the successor's recovered_up_to, or that materialize.FromEpoch refuses/clamps when a later epoch's recovery point exists; plus a unit case in internal/recovery for the same ordering.

- **Reopening a WAL restarts sequences at 1 and serves an empty read view** _(wal-durability)_
  - failure mode: The documented ATTACHING→ACTIVE path (§16: 'validar epoch + obtener lease', not 'increment epoch') lets an agent restart re-attach at the same epoch. The rebuilt Log serves zeros for data that is in the WAL and in S3, re-issues sequences 1..N under the same (volume, epoch) — which is the trigger for the GCM nonce reuse and for duplicate/overlapping object spans — and every durability claim for that epoch is then built on duplicated sequence numbers.
  - missing test: A DST scenario 'crash mid-workload, reopen the log, resume' asserting the resumed log's first sequence is last_local+1, its read view equals the pre-crash view, and no S3 object span is reissued; failing that, a unit test that NewLog over a non-empty file is refused.

- **AES-GCM nonce reuse when the sequence restarts inside the same (volume, epoch)** _(wal-durability)_
  - failure mode: A Log rebuilt for the same volume at an unchanged epoch (agent restart, re-attach that validates rather than bumps the epoch) re-issues sequences 1,2,3… under the same DEK and epoch. Two WAL objects in the bucket then carry ciphertexts whose XOR is the plaintexts' XOR — guest data recoverable without the key (INV-15), and forgeable records that pass DEK.Open and the plaintext CRC.
  - missing test: Not a crypto test — a WAL-level test that a Log which resumes over a non-empty WAL for an unchanged epoch either refuses to start or resumes at last_seq+1, i.e. the same resume test the reopen finding needs; plus a DST checker that no (volume, epoch, sequence) is ever sealed twice across a run.


### MEDIUM

- **A duplicate drain request re-cordons a host that was returned to ACTIVE (the DEAD arm is by design)** _(drain-placement-dst)_
  - failure mode: A retried or replayed drain request for a finished operation silently removes a repaired, ACTIVE host from placement again — capacity disappears from the fleet while the call reports SUCCEEDED and reports no error anywhere for an operator to see.
  - missing test: Assert that a duplicate of a terminal drain operation performs no host-state transition (the cordon must move behind the terminal short-circuit).

- **The drain never re-checks the destination, and Promote grants a host lease unconditionally** _(drain-placement-dst)_
  - failure mode: The chosen destination dies or stops heartbeating during the (potentially long) materialization: the volume's primary is set to a dead host, its capacity is committed there and the source's released — the volume is stranded with no writer. Worse, the CP has just written a fresh last_renewal for a host that never took the grant, so the failover *away* from it must wait a full lease_ttl+max_clock_skew from that timestamp, and because the lease is per host that renewal also extends the fence covering every other volume already on it.
  - missing test: A drain test where the chosen destination is marked DEAD after placement and before promotion (assert the move aborts and the reservation is released), and a promotion test asserting no lease is granted to a host that is not ACTIVE.

- **DST: 17 of 21 mandatory scenarios ignore the seed** _(drain-placement-dst)_
  - failure mode: The gate advertises a six-seed fault-injection matrix over the durability and fencing paths while exploring one interleaving of one fault set. No seed-driven throttling, lost response, or crash point ever touches the drain, promotion or recovery-point code — which is exactly why the trivially reproducible drain bugs above (double release, foreign-promotion boundary, op-id reuse) have gone unnoticed.
  - missing test: Seed-driven fault decisions in the fencing/drain/recovery scenarios: a random crash point among the drain's boundaries (place → reserve → bulk materialize → promote → final materialize → boundary → release) and seed-driven Store.InjectThrottle/InjectLostResponse during materialization and the boundary PUT, with the post-conditions asserted after resume.

- **DST: the drain scenario never asks whether the old writer can still ACK** _(drain-placement-dst)_
  - failure mode: The scenario that names INV-09/INV-10/INV-11 for the drain would still pass if the source kept a valid lease and kept ACKing writes into the old epoch after the promotion — the exact way a drain loses an ACKed write, and precisely the hole left open by the missing lease revocation.
  - missing test: Give the drain scenario's source a real lease.Manager, and after the drain have it attempt Write+Flush asserting wal.ErrSelfFenced, emitting EventDurableAck{LeaseValid} plus an EventFailover whose Recovered is recomputed from S3 *after* the late attempt; plus a planted-bug proof that flips real production behaviour (e.g. a lease that stays valid) rather than emitting a literal event as planted_bug_test.go does today.

- **Epoch numbers can be re-used after a coordinated restore, and nothing detects two writers in one (volume, epoch) key namespace** _(fencing-promotion)_
  - failure mode: A DR restore rolls both PostgreSQL and the bucket back to a point where the volume was at epoch 5, while epochs 6-8 were used and their wal/<vol>/6../8/ objects survive (or were also restored). The next promotion grants 6 again; the new writer writes sequences into a namespace that already holds another writer's objects. Depending on where the batch boundaries fall, recovery either truncates the contiguous prefix at the first duplicate first-sequence (silently under-reporting the durable point) or splices two writers' records into one "valid" volume history — block-level corruption presented as a validated durable point.
  - missing test: `TestCompareAndAdvanceRefusesToGoBackwards` / to the same value (defence in depth at the store, not by caller convention); a recovery test that two objects covering overlapping sequence ranges in one (volume, epoch) are detected as two writers rather than silently ending or splicing the prefix; and a DST scenario `epoch-object-restored-from-backup` replaying a cached ETag against a rolled-back object.

- **The CP term has no anchor outside PostgreSQL, so a PITR restore lets a new leader re-issue a term a live leader is already using** _(fencing-promotion)_
  - failure mode: The CP database is restored from backup/PITR to a point where term = 7 while the incumbent CP process is still running at term 9. A newly started CP acquires 8, then 9 — now two processes are simultaneously "the leader" at the same term: both can BumpVolumeEpoch, RenewHostLease, and drive drains/promotions of the same volume, and the §7 ErrStaleTerm defence is silently disabled during exactly the incident where two CPs running at once is most likely.
  - missing test: An integration test that a term-rewound leader row cannot re-issue a term already witnessed outside PG — e.g. the leader term is fenced by the highest epoch/term stamp observed in S3, and AcquireLeadership refuses (or jumps past) a value at or below it.

- **Drain resume infers prev_epoch = current_epoch - 1, so a double advance writes a permanent epoch boundary of zero** _(fencing-promotion)_
  - failure mode: An unrelated failover, a duplicate promotion, or a concurrent drain advances the volume's epoch twice between drain passes. The resumed pass materializes epoch current-1, which holds no objects, and permanently records recovered_up_to = 0 as the boundary for the new epoch. recovery.prefixFloor (recovery.go:151-157) then uses 1 as the floor for the new epoch while the new writer continues numbering from the true previous end, so the contiguity walk breaks at the first object and the whole epoch reads as durable = 0 — every ACKed write in it is silently reported as not durable.
  - missing test: `TestDrainResumeWhenTheVolumeWasPromotedTwice` — bump the epoch twice (or promote it elsewhere) between passes and assert the drain refuses rather than writing a boundary derived from a guessed prev_epoch; the previous epoch should come from the recovery-point chain or the operation's recorded plan, not from subtraction.

- **The fencing deadline compares PostgreSQL's now() with the CP's own wall clock, and only the safe (lagging) skew direction is tested** _(fencing-promotion)_
  - failure mode: The CP container's wall clock steps forward (NTP correction, VM restored from a snapshot, bad RTC) by more than max_clock_skew relative to the database server. p.clk.Wall() is ahead of PG's now()-derived last_renewal by that amount, so the fencing wait is shortened by exactly the offset and epoch N+1 is granted while the old writer's monotonic lease is still valid — the precise window INV-11 exists to close — with no test or runtime check able to notice.
  - missing test: The positive-skew twin of TestDriftOnlyLengthensTheWait: a CP wall clock ahead of the clock that stamped last_renewal must still not grant early (which means measuring the wait against a source the CP cannot skew — PG's now() on both ends, or a monotonic dwell since the CP first observed the lease), plus an assertion somewhere that the CP↔PG offset is bounded by max_clock_skew before a promotion proceeds.

- **The §7 volume failover state machine is never driven: no Store method exists to move a volume through FENCING_WAIT/RECOVERY_REQUIRED** _(fencing-promotion)_
  - failure mode: There is no durable record that a volume is mid-fence, so two reconciler passes, two CP goroutines, or a CP plus an operator each see an ACTIVE volume and each start a promotion — nothing makes the second one back off. The guarantee the promotion protocol is documented to rest on is enforced by no running code, so a future caller can jump straight to recovery and no test would notice.
  - missing test: A term-guarded, transition-guarded SetVolumeState on metadata.Store with a promoter that marks FENCING_WAIT before the wait and RECOVERY_REQUIRED after the epoch is granted, plus a test that a second concurrent promotion attempt observes FENCING_WAIT and refuses, and an end-to-end test driving one volume through the §7 states.

- **Two drains of the same host under different operation ids release the source's committed capacity twice** _(fencing-promotion)_
  - failure mode: Op1 and op2 both plan hostA while V is still there. Op1 moves V and releases volSize from hostA. Op2 later reaches V, takes finishMovedVolume with its own empty progress, and releases volSize again: if hostA holds other volumes' reservations those bytes are silently consumed and placement over-subscribes the host until the NVMe fills; if it does not, CommitHostCapacity returns ErrCapacityUnderflow and the second drain fails hard mid-evacuation, leaving the operation FAILED on a host the operator believes is emptying. Op2 also re-materializes and re-asserts epoch boundaries for volumes it never owned.
  - missing test: `TestTwoDrainsOfTheSameHostReleaseCapacityOnce` — two operation ids interleaved over one host, asserting the source's committed bytes end at exactly its remaining reservations — plus a guard that a volume is only finished by the operation that planned its move.

- **Promote grants a lease to the new host without checking it exists or is ACTIVE, and sim and pg disagree about what that does** _(fencing-promotion)_
  - failure mode: A direct promotion to an unregistered or since-removed host: in production PG's FK rejects the final step *after* the epoch has already been bumped in PostgreSQL and CASed in S3, so the old writer is fenced and the intended new writer has no lease — nobody can ACK a FLUSH for that volume until a human notices. In simulation the same call succeeds, so every DST fencing conclusion is drawn against a store more permissive than the one production uses.
  - missing test: A promoter test that promoting to an unknown/DEAD/CORDONED host is refused *before* any epoch is advanced, and one conformance suite for metadata.Store run against both sim and pg so the two cannot diverge on lease/term semantics.

- **Reachability and marking use two independent, non-atomic LIST calls, and LIST is documented eventually consistent** _(gc-objectstore)_
  - failure mode: A bucket-wide sweep that GETs every manifest takes minutes. A snapshot manifest published inside that window anchors objects that are already older than grace, so the Reachable snapshot is stale by the time Mark lists again and the newly-anchored live objects are marked — data loss with correct code on both sides of the race. The reverse (anchor listed, objects not yet) makes a sweep look clean over an inconsistent bucket.
  - missing test: internal/gc: a case that publishes a manifest between the Reachable and Mark calls asserting nothing anchored is marked, and one on a sim store with SetEventualList(true) where the anchor is unsettled but its objects are visible. Structurally, Mark should consume the listing Reachable used rather than re-listing.

- **A rewrite over a marked key destroys the marked version in both in-process stores, and the contract test blesses it** _(gc-objectstore)_
  - failure mode: 'GC marks X → the agent's idempotent retry (or any writer) PUTs X again → operator performs the un-GC runbook step' returns the new bytes, not the marked ones. If the rewritten object differs in length or content from what was marked, the reconstructed volume is corrupt rather than merely short — and on the filesystem store Restore returns ErrNotFound, so the operator gets 'nothing to restore' while believing the data is back.
  - missing test: storetest: 'restore after a rewrite returns the marked version's bytes' — or an explicit contract statement that sim and the filesystem store are single-version, with the DST harness forbidden from claiming reversibility after a rewrite. Plus the S3-backed case on a versioned bucket restoring by VersionId.

- **The filesystem store clears the delete marker before writing, and writes without atomicity or fsync** _(gc-objectstore)_
  - failure mode: An object an operator believes is retired silently comes back and is served (ENOSPC on a full disk, EIO, or a crash between the Remove and the WriteFile). Or a crash mid-WriteFile leaves a zero-length/torn file that is now a visible 'object' at a create-only key that can never be repaired — the retry gets ErrPreconditionFailed, and recovery's integrity check then permanently truncates the durable prefix at that object.
  - missing test: internal/simio/real: fault-injected write failures (full disk / short write / crash between marker removal and write) asserting the store never leaves a partially written object visible and never resurrects a marked one; plus a durability test that Put survives a simulated crash (temp file + rename + fsync of file and parent dir).

- **The S3 wrapper's error translation has no unit test and misses AWS's 409 ConditionalRequestConflict** _(gc-objectstore)_
  - failure mode: On AWS S3 (or any backend other than the pinned one), a promoter that genuinely lost the fencing race gets an opaque unmapped error instead of ErrCASConflict, so the 'I was fenced' branch is never taken — promotion aborts with an unexplained failure, or is retried on the wrong assumption. Fail-closed, so not data loss, but the fencing path behaves differently from every proof written about it and is undiagnosable in an incident.
  - missing test: A pure unit test over translate() with a table of synthetic smithy.APIError codes → expected sentinel (no backend needed): ConditionalRequestConflict, SlowDown, ServiceUnavailable, RequestTimeout, AccessDenied, InternalError, and NoSuchBucket mapped to something distinguishable from a missing key. Plus an integration case racing 16 conditional PUTs *through S3Store* asserting every loser gets ErrPreconditionFailed.

- **sim CreateVolume/CreateSnapshot silently overwrite an existing id where pg raises 23505** _(metadata-cp)_
  - failure mode: Two operators run rebuild-metadata concurrently against Postgres: both see ErrNotFound for the same volume, both INSERT, the loser aborts with `duplicate key value violates unique constraint volumes_pkey` after having created an arbitrary prefix of the catalog, and returns a RebuildResult whose Volumes count reads as a complete rebuild. On the sim the same sequence is silently fine, so no test can see it.
  - missing test: In the shared contract suite: CreateVolume/CreateSnapshot against an existing id must have one documented outcome (error, or a proven no-op) and must never lower current_epoch, blank primary_host_id, or reset watermarks; plus a concurrent-rebuild test in rebuild_catalog_test.go asserting the second runner converges instead of aborting.

- **A PG restore that rewinds control_plane_leader.term re-issues a term that a partitioned CP still holds** _(metadata-cp)_
  - failure mode: CP-b holds term 2 and is partitioned but alive. Operators PITR-restore the CP database to a backup where term=1; CP-c acquires and is granted term 2. Both now pass `(SELECT term FROM control_plane_leader) = 2` on every mutation: both release capacity, both drive drains from different plans, both set primary_host_id. No error is raised anywhere and the accounting diverges from reality.
  - missing test: An integration test that rewinds control_plane_leader.term behind the CP's back and asserts a previously-issued term is rejected — which needs a design answer first (a term anchored outside the restorable row, or startup reconciliation against the S3 epoch objects), recorded as an ADR.

- **nullUUID coerces a malformed id to SQL NULL instead of erroring** _(metadata-cp)_
  - failure mode: A clone (or, once a caller exists, a promotion) is issued with a host id that was truncated or read from an unset config field. The store returns nil; the volume row exists with primary_host_id NULL, so ListVolumesByHost never returns it — a drain of that host reports success without evacuating it, and Promote's resume branch `v.PrimaryHostID == newHost` can never match, so a retry bumps the epoch again.
  - missing test: Contract test asserting every id argument that is not a valid UUIDv7 returns an error rather than being coerced to NULL, for CreateVolume, BumpVolumeEpoch, CreateSnapshot and RecordOperation, including the empty string where empty is not meaningful.

- **pg RecordOperation reports a stale-term rejection as recorded=false, so a zombie CP's Cancel returns success** _(metadata-cp)_
  - failure mode: An operator cancels a not-yet-started drain through a CP that has already lost the election. Cancel returns nil, the API reports success, no row is written, and the real drain keeps promoting volumes. More generally the one mutation whose purpose is admin idempotency (INV-21) cannot tell 'already done' from 'you are not the leader', so every caller that branches on `recorded` branches wrongly for a zombie.
  - missing test: Assert ErrStaleTerm — distinct from recorded=false — for RecordOperation, CreateSnapshot and UpdateOperation in both implementations, plus a Cancel-under-stale-term test in drain_test.go asserting the error surfaces.

- **UpsertHost overwrites state and nvme_committed_bytes with no transition guard** _(metadata-cp)_
  - failure mode: Once a heartbeat path exists: a host is cordoned and drained with 700 bytes committed; its next routine heartbeat carries State: ACTIVE and whatever nvme_committed_bytes the agent believes (0). The row flips back to ACTIVE — HostState.AcceptsPlacement() starts handing it new volumes while its own are being evacuated — and the committed counter is zeroed, so placement overcommits the host and the in-flight drain's later release underflows.
  - missing test: A test in both implementations that reserves capacity and cordons a host, issues a heartbeat-shaped UpsertHost, and asserts state and nvme_committed_bytes are unchanged — i.e. UpsertHost must not carry those columns, or must be transition-guarded like SetHostState.

- **BumpVolumeEpoch is a blind increment with no expected-epoch CAS, and no concurrency test exists anywhere in the CP** _(metadata-cp)_
  - failure mode: An epoch is burned; PG records as owner a host that never CASed the epoch object and never got a lease, while the host that did win holds a lower epoch. Every later read of primary_host_id — the drain's ListVolumesByHost, Promote's resume branch, rebuild — is wrong about who owns the volume, and the resume branch will silently fence the legitimate writer.
  - missing test: N concurrent BumpVolumeEpoch calls asserting exactly one succeeds per expected epoch (which requires adding an expected-epoch parameter), plus a concurrent-Promoters test in promotion_idempotency_test.go.

- **Missing-row and shrink error identities are inverted between sim and pg** _(metadata-cp)_
  - failure mode: A reconciler that treats ErrStaleTerm as 'step down and re-acquire leadership' loops forever stepping down over a volume that was simply deleted; one that treats ErrShrinkNotAllowed as a permanent client error returns a bogus 4xx for what was actually a lost election. Because the sim answers the opposite way, no simulation test can catch either.
  - missing test: Contract test pinning the error identity of every mutation for: missing row, stale term, and both together (specifying which wins) — and a concurrent-writer case for the read-after-write disambiguation paths.

- **The volume and snapshot lifecycles the schema declares are unreachable through the Store, and a raw-SQL test makes them look covered** _(metadata-cp)_
  - failure mode: A volume mid-promotion is persisted as ACTIVE, so a CP restart or a second CP has no durable signal that it is being fenced and can start a competing attach. A snapshot whose publication crashed stays CREATING forever with nothing able to move it to FAILED or DELETING, so the catalog side of GC never sees it and its objects are never collected. When these mutations are eventually added there is no precedent test forcing the atomic `state = ANY(allowed_states)` predicate — the sim's read-modify-write shape (sim.go SetHostState) is the one most likely to be copied.
  - missing test: A test asserting the Store can express each lifecycle it stores (or an explicit, tested statement that the vocabulary is deliberately narrower than the schema), plus a transition-guard test for volumes and snapshots equivalent to TestPGOperationPhaseGuardIsAtomic including a concurrent-writer case proving the guard lives in the UPDATE predicate.

- **checkpoint.Create is not idempotent across a crash between Publish and AdvancePublished: local truncation is blocked until the next write** _(recovery-materialize)_
  - failure mode: A checkpoint PUT persists but its response is lost (or the process dies between the two steps). Every retry fails with ErrPreconditionFailed and the published watermark never advances, so local WAL for that volume cannot be truncated while it stays idle — the host's NVMe fills, which stalls writes for that volume and every co-tenant on the disk. Symmetrically, a *different* checkpoint already present at the same sequence — the signature of two writers claiming one epoch — is reported as an ordinary precondition failure and never surfaces as the fencing violation it is.
  - missing test: In internal/checkpoint/checkpoint_test.go: publish the checkpoint Create would have written (or use sim.InjectLostResponse on that PUT), then call Create and assert it treats a byte-identical existing checkpoint as success — advancing published so TruncateLocal is permitted — and treats a *different* checkpoint at the same sequence as a hard, distinguishable error.

- **A summary that over-claims makes recovery of that epoch a permanent hard error, and the summary is overwritable and never validated against its own volume/epoch** _(recovery-materialize)_
  - failure mode: One object inside the epoch is lost, delete-marked, or fails validation while the summary still names the last uploaded sequence. Recovery of that epoch becomes impossible on every retry: DurablePoint errors, FromEpoch errors, drain.move and finishMovedVolume fail, so the volume can neither be evacuated off a failing host nor promoted, and no telemetry reports the discrepancy. Because the key is overwritable and its own fields are unchecked, a stray or mis-keyed summary is enough to brick a volume's recovery until a human deletes an object.
  - missing test: (a) A test that the honest, shorter prefix is still recoverable (or that the discrepancy is reported as a distinct, actionable error) when the summary over-claims — plus a drain test for a volume in that state. (b) A summary whose VolumeID/Epoch fields belong to another volume/epoch must be ignored or rejected, not trusted. (c) A summary that claims *less* than the contiguous prefix must be pinned by a test now, before the documented §22.1 optimisation of starting the LIST from the summary turns today's harmless skip into a silent under-report.

- **A lagging LIST silently reports a zero durable prefix; nothing constrains the durable point to be monotonic** _(recovery-materialize)_
  - failure mode: A promotion or drain runs while LIST is behind (a lagging S3-compatible backend, a LIST racing an in-flight upload). recovery.DurablePrefix returns a value below what the fenced writer ACKed, with no error, and drain writes that number into the create-only recovery point for the next epoch — those ACKed FLUSHes end up below the new floor permanently, an ACKed write lost purely because a listing was stale.
  - missing test: Either (a) tighten the Store contract doc to require strongly consistent LIST and let integration/backend/conformance_test.go TestListSeesAFreshPut be its enforcement, or (b) recovery/drain tests plus a DST scenario with SetEventualList(true) asserting the durable point never regresses below a previously observed value and that the boundary write refuses to lower it. Option (b) is the same guard the recovery-point monotonicity gap needs.

- **'Same range, different hash ⇒ hard fail' (INV-21 / §14.5) is unreachable because the key embeds the content hash** _(wal-durability)_
  - failure mode: Two objects claiming the same sequence span with different content both pass create-only PUT, both pass recovery.validate, and Recover applies both — the recovered volume content is decided by SHA-prefix sort order, with no diagnostic anywhere. Reachable when a restarted/re-batching writer regroups records (see the reopen finding) or when fencing has already failed and two writers share an epoch — exactly the case INV-21 exists to catch.
  - missing test: In internal/wal/uploader_test.go: upload two ClosedBatches with identical [First,Last] and different Records through the real key builder and assert the second is refused. In internal/recovery/integrity_test.go: assert DurablePrefix/Recover refuse a span covered by two distinct validated objects rather than silently picking one.

- **Overlapping sequence spans silently under-report the durable point** _(wal-durability)_
  - failure mode: Overlapping objects (producible after a restart/re-batch, not by a single correct Batcher) make the durable point stop early. W2 then writes recovery-point{recovered_up_to: 3}, epoch N+1's floor becomes 4, and sequences 4-5 — inside an ACKed FLUSH — are never replayed by anyone again, while the drain's materializer refuses the same volume outright.
  - missing test: Cases in TestDurablePrefix for {1-3},{2-5} and {1-3},{1-5} asserting the durable point still reaches 5 via record-level contiguity, or that recovery fails loudly instead of returning 3; and a matching assertion that materialize.FromEpoch and DurablePrefix agree on that layout.

- **A FUA WRITE completes without fdatasync, without a PUT and without a lease check** _(wal-durability)_
  - failure mode: A caller that hands a virtio FUA write to Log.Write gets a completed write whose bytes are only in the host page cache, with no fdatasync, no verified PUT and no lease validation — the flag is accepted and half-handled, which reads as 'FUA is implemented'. Host loss then loses a write the guest believes is on stable media. Severity is capped today only because the component that would ACK to a guest does not exist (DEV-0007) and Write's doc comment claims no-sync semantics for normal writes — so the real defect is an undecided contract with a flag silently swallowed.
  - missing test: In internal/wal/durability_test.go, the three assertions that already exist for Flush, applied to a FUA write: it must be in a verified S3 object by the time Write returns, return ErrSelfFenced when the lease expired, and return ErrNoLease in remote mode with no lease checker — or, if translation is the agent's job, a test that Log.Write rejects FlagFUA outright.

- **Remote-mode FLUSH ACKs and advances durable with nothing in S3 when the log has a lease but no uploader** _(wal-durability)_
  - failure mode: A Log built with NewLog + SetLease (remote is the default mode) ACKs a FLUSH as remotely durable with zero bytes in the object store and advances durable_sequence past anything S3 can produce — the same fail-open shape DEV-0004 removed, re-entered through the vestigial setter. Severity is medium rather than high because no production caller exists and the setter is dead code; the fix is deleting it so EnableRemote is structurally the only way into remote mode.
  - missing test: In internal/wal/durability_test.go next to TestRemoteModeWithoutALeaseFailsClosed: a remote-mode log with a lease but no uploader must fail closed; and an assertion in the happy path that a successful Flush left at least one object in the store covering target.

- **WAL records never carry their VolumeID, so a record can be replayed under the wrong volume undetected** _(wal-durability)_
  - failure mode: The local WAL file has no volume binding whatsoever: a file replayed against the wrong volume (path bug, restored backup, reused volume directory), or records of two volumes concatenated, apply to the wrong guest's extents with no error. Inside an object the record-level epoch is likewise unchecked against the object header. Encrypted volumes are saved only by the GCM AAD, which is not the layer INV-05/INV-08 are claimed at.
  - missing test: A field assertion in internal/wal (or format) that a record written through Log.Write/Discard/WriteZeroes carries the log's volume id and epoch; and a validate() extension in internal/recovery rejecting any record whose VolumeID/Epoch disagrees with the object header, with a planted violation to prove the checker catches it.

- **A full disk is not modelled anywhere; the WAL has no ENOSPC policy** _(wal-durability)_
  - failure mode: The device fills because S3 has been unreachable and nothing was truncated. The first ENOSPC arrives as a partial append (the silent-truncation failure above); after that every WRITE returns a raw I/O error while the volume reports itself un-fenced, durable_sequence is stale, and no metric or state says 'out of space'. Recovery from a WAL whose tail was cut by ENOSPC is untested.
  - missing test: InjectENOSPC(name, afterBytes) in internal/simio/sim/disk.go with the real-disk mapping, plus a DST scenario 'disk fills under sustained write with S3 down' asserting WRITEs get ErrBackpressure before the device fills, the log enters an explicit degraded state, and the WAL replays cleanly afterwards.


### LOW

- **Placement is advisory: CommitHostCapacity enforces no oversubscription limit** _(drain-placement-dst)_
  - failure mode: A drain plus a clone (or two drains) racing on the same destination push its committed bytes past MaxOversubscription * NVMeTotalBytes — the bound §28.2 declares — and nothing on the write path re-checks it, so the host over-fills its NVMe and the ratio alert only fires after the fact. Bounded in practice: subsequent placements see the over-committed host and refuse it, no data is lost, and there is no CP daemon running operations concurrently yet.
  - missing test: A metadata-level test that CommitHostCapacity rejects a delta that breaks the declared policy (the limit belongs in the reserving query), plus a controlplane test with two placements racing one destination.

- **A stale-term drain leaks the destination's reservation silently** _(drain-placement-dst)_
  - failure mode: Leadership changes between the capacity commit and the promotion: the destination keeps a phantom reservation for a volume it never received, nothing reconciles it, and the host's committed ratio is permanently wrong — placement under-uses and eventually refuses a host that is actually empty. No data loss, and a new leader could recompute the accounting.
  - missing test: Drain called with term-1 asserting nothing is mutated; and a move where the term is invalidated between the capacity commit and the promotion, asserting the reservation is not leaked (or that the failure is surfaced rather than swallowed).

- **A lease grant delivered after Revoke re-arms the lease (Grant carries no generation/epoch token)** _(fencing-promotion)_
  - failure mode: The agent revokes on an accepted fence or detach while a grant issued before the fence is still in flight. The response lands after the fencing wait has elapsed and the CP has promoted elsewhere; Grant() re-arms the lease with a fresh t0 and the log resumes ACKing FLUSH for a volume it no longer owns. Two writers.
  - missing test: A lease generation/epoch token threaded through Grant (Grant(gen) ignored when gen predates the last Revoke) with a unit test, and a DST scenario delivering a grant response after a fence.

- **Two overlapping sweeps abort each other at the first already-marked key, and the reported totals are wrong** _(gc-objectstore)_
  - failure mode: A cron sweep that overruns into the next one, or an operator running the sweep by hand alongside it, makes one pass die early with an opaque ErrNotFound. gc_marked_bytes_total then reports a truncated pass, and orphan_objects_total is a gauge set to *this* pass's count (gc.go:124), so after the first pass it reads 0 while the bucket may be full of marked-but-unswept objects — an operator cannot tell the GC is stuck.
  - missing test: internal/gc: two interleaved sweeps against one store asserting both complete and the union of marks is exact; a throttle injected at the k-th Delete for every k (table-driven) asserting the next pass resumes and the totals are true. A storetest case pinning whether Delete of an already-marked key is ErrNotFound or a no-op, since sim/fs and S3Store disagree.

- **Structural keys are unconditionally reachable and reachability is one level deep, so retiring any anchor widens the mark set** _(gc-objectstore)_
  - failure mode: A routine cost-control lifecycle rule on `checkpoints/`, or an operator expiring an old snapshot manifest, silently makes the WAL objects that anchor solely retire with it; the next sweep marks them. Invisible until a recovery reads a short prefix. A clone's manifest does not protect its parent's objects if the parent manifest is the thing that was expired.
  - missing test: internal/gc: a test where an anchor is removed or expired and the sweep must not widen its mark set; a test that a child manifest keeps its parent's objects reachable through ParentSnapshotID; and a bound on structural growth (structural objects must themselves be retirable) so the lifecycle rule is never needed.

- **Watermarks can move backwards and are not epoch-qualified at the store** _(metadata-cp)_
  - failure mode: Once agents report watermarks: an epoch-N primary's report is queued behind a retry and delivered after epoch N+1's writer has published its own. Promotion does not change the CP term, so the stale report passes the term guard and lowers durable_sequence — during an incident that is the number an operator uses to decide whether to accept data loss.
  - missing test: Contract test asserting UpdateWatermarks rejects (or ignores) a decrease and rejects published > durable > local in both implementations, plus a fencing test where an epoch-N report arrives after epoch N+1 has published.

- **Uploader retries with no backoff and no context check** _(wal-durability)_
  - failure mode: Under coordinated backend throttling a FLUSH exhausts its budget faster than the backend's recovery window and returns ErrUploadRetriesExhausted where a short backoff would have succeeded; on a cancelled context the loop still issues maxAttempts requests instead of returning at the first ctx.Err().
  - missing test: An uploader test with an injected clock asserting a sleep drawn from the simulated clock between attempts on a throttle (per INV-01), and a test that a cancelled context aborts the retry loop at the first iteration.
